= HTTP with Post-Quantum Cryptography (PQC): A Camel Quarkus example (Java 25)
:cq-example-description: An example that shows how to implement quantum-resistant TLS using the JDK's own hybrid X25519MLKEM768 key exchange, configured through the Quarkus TLS registry, without Bouncy Castle

{cq-description}

This example serves a Camel `platform-http` endpoint over mutual TLS 1.3 protected by the hybrid post-quantum key exchange **X25519MLKEM768** (classical X25519 ECDH combined with ML-KEM-768, NIST FIPS 203).

Unlike the `http-pqc-j21` example, it uses **no Bouncy Castle at all**:

[cols="1,2,2"]
|===
| | `http-pqc-j21` | `http-pqc-j25` (this example)

| TLS provider
| Bouncy Castle JSSE, registered in code
| JDK SunJSSE

| PQC configuration
| `jdk.tls.namedGroups` system property
| Quarkus TLS registry: `quarkus.tls.key-exchange-groups` and `quarkus.tls.pqc-enforcement-policy`

| Certificates
| Generated at startup with the Bouncy Castle X.509 API
| Generated at build time with the JDK `keytool`

| Extra dependencies
| `camel-quarkus-support-bouncycastle`, `bctls-jdk18on`
| none
|===

IMPORTANT: Requires a JDK with X25519MLKEM768 in SunJSSE (https://openjdk.org/jeps/527[JEP 527]): **JDK 25.0.5 (October 2026 update) or newer, or JDK 27+**. On older JDK 25 builds the application fails at startup with `PQC enforcement policy ... requires X25519MLKEM768 but the configured SSL engine does not support it`. Check your JDK (the output must contain `X25519MLKEM768`):

[source,shell]
----
echo 'System.out.println(String.join(",", javax.net.ssl.SSLContext.getDefault().getSupportedSSLParameters().getNamedGroups()))' | jshell -q
----

NOTE: CI runs with JDK 17 and 21, therefore the tests of this example are skipped there (via the `jdk-older-than-25` profile).

TIP: Check the https://camel.apache.org/camel-quarkus/latest/first-steps.html[Camel Quarkus User guide] for prerequisites and other general information.

== Configuration

The whole PQC setup is in `src/main/resources/application.properties`:

[source,properties]
----
quarkus.tls.protocols = TLSv1.3
quarkus.tls.ssl-engine = jdkssl
quarkus.tls.key-exchange-groups = X25519MLKEM768,x25519,secp256r1
quarkus.tls.pqc-enforcement-policy = client-negotiated
----

`quarkus.tls.pqc-enforcement-policy` values:

* `client-negotiated` (default here): X25519MLKEM768 is preferred, classical clients can still connect. Use it for gradual migration.
* `strict`: only post-quantum hybrid groups are accepted, classical clients are rejected.
* `relaxed` (Quarkus default): the configured groups are still applied as-is, but PQC is neither enforced nor checked at startup (Quarkus logs a warning saying the groups are ignored). Do not use it for this purpose.

Both `client-negotiated` and `strict` fail at startup when the JDK does not support X25519MLKEM768, so the server never silently falls back to classical-only TLS.

== Certificates

The Maven build (`generate-resources` phase) runs `keytool` to create fresh demo certificates in `target/certs/` (password `changeit`):

* `server-keystore.p12`, `server-truststore.p12` - server identity (`CN=localhost`, SAN `localhost`, `127.0.0.1`) and trusted client
* `client-keystore.p12`, `client-truststore.p12` - client identity and trusted server
* `server-cert.pem`, `client-cert.pem` - the same certificates in PEM form (e.g. for `curl --cacert`)

The certificates use classical RSA signatures. The post-quantum protection comes from the key exchange, which defeats "harvest now, decrypt later" attacks on recorded traffic.

TIP: JDK 24+ `keytool` can also create ML-DSA certificates (`-keyalg ML-DSA-65`). This example keeps RSA because ML-DSA signatures in TLS are not yet supported by SunJSSE in JDK 25.

== Start in Development Mode

[source,shell]
----
mvn clean compile quarkus:dev
----

The application starts on a random HTTPS port with mutual TLS. Look for `Listening on: https://localhost:xxxxx` in the log. Endpoint: `/pqc/secure`.

Any JDK 25.0.5+ client offers X25519MLKEM768 by default. Clients without PQC support (e.g. most `curl` builds) fall back to x25519 thanks to `client-negotiated`:

[source,shell]
----
curl --cert target/certs/client-keystore.p12:changeit --cert-type P12 \
     --cacert target/certs/server-cert.pem \
     https://localhost:xxxxx/pqc/secure
----

NOTE: The response text describes the hybrid key exchange; a classical client connected through the fallback does not get it.

[source,shell]
----
mvn clean package
java -jar target/quarkus-app/quarkus-run.jar
----

=== Native Mode

IMPORTANT: Native mode requires having GraalVM and other tools installed. Please check the Prerequisites section of https://camel.apache.org/camel-quarkus/latest/first-steps.html#_prerequisites[Camel Quarkus User guide].

The native image must be built by a GraalVM / Mandrel release based on JDK 25.0.5 or newer, otherwise it lacks X25519MLKEM768 and fails at startup.

[source,shell]
----
mvn clean package -Dnative
./target/*-runner
----

== Testing

[source,shell]
----
mvn clean test
----

The tests call the server with the JDK TLS stack, restricting the named groups offered by the client:

* `PqcWithFallbackTest` (`client-negotiated`): hybrid client ✓, classical-only client (`x25519,secp256r1`) ✓
* `PqcOnlyTest` (`strict`, via `PqcOnlyProfile`): hybrid client ✓, JDK default client ✓, classical-only client ✗ (TLS handshake fails)

Native mode runs `PqcWithFallbackIT` only, because a native executable is built with one configuration:

[source,shell]
----
mvn clean verify -Dnative
----

NOTE: The tests use RestAssured (Apache HttpClient) rather than `java.net.http.HttpClient`, because the latter ignores `SSLParameters.setNamedGroups()`.
